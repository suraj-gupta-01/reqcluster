# ReqCluster Dependency Engine — Hardening Plan

**Scope:** Fix the DP5 dependency tree engine's soundness, robustness, and explainability gaps, in this order:
1. Evaluation harness (build first — everything else is unmeasurable without it)
2. spaCy-based artifact extraction + embedding near-match (main fix — Option 3)
3. On-demand, click-triggered per-edge explanation (Option 5, scoped)

**Explicitly out of scope for this pass:** replacing Pass 2's scoring formula with an LLM or a trained classifier pipeline-wide (rejected earlier for scale/reliability reasons — 8K+ candidate pairs at 1,000 requirements × ~6.7s/local-LLM-call is untenable, and local-model output is only 88% reliable even after the enrichment parser fix). Pass 2's arithmetic scoring stays as-is in this iteration; the harness will tell you if it's actually the bottleneck worth spending the *next* iteration on.

---

## Phase 0 — Baseline (½ day)

Before touching any extraction logic, capture the current engine's numbers so every later change has a before/after.

**Tasks:**
- Run the existing engine against `data/aerospace_requirements.csv` (already hand-built with "intentional dependency structure") and record raw edge output.
- Stand up the harness (Phase 1) far enough to score *today's* engine. This is the control group.

**Exit criterion:** a checked-in `baseline_metrics.json` with precision/recall/F1 for the current regex-based engine. If you skip this, you cannot prove Phase 2 actually helped.

## Phase 1 — Evaluation Harness

**Goal:** turn "we think it's better" into a number, the same way `metrics.md` does for clustering (purity/ARI/V-measure).

### 1.1 Gold-standard dataset

- Extend `data/aerospace_requirements.csv` (64 rows, 8 subsystems) with a companion gold-edge file: `data/aerospace_requirements_gold_edges.csv`, columns `source_id, target_id, relation` (`hierarchical | sequential | data | reference`), hand-labeled by re-reading each requirement pair that *should* have a dependency.
- Also generate a **harder, adversarial set** specifically designed to stress the known gaps: passive voice ("shall be generated by..."), coordinated artifacts ("altitude and heading data"), and artifact synonyms ("temperature reading" vs. "temp value"). ~30–40 requirements is enough — this set exists specifically to prove Phase 2 worked, not to be representative of "normal" data.
- **Stretch, not blocking:** pull a subset of Dronology (README already flags it as having real ground-truth trace links) if time allows — it's the more credible external validation to cite to judges versus a self-authored gold set.

### 1.2 Scoring module

New file: `backend/core/dependency_eval.py` (pure function, no DB/LLM — consistent with the rest of `core/`).

```python
def score_dependency_tree(
    predicted_edges: list[dict],   # output of build_dependency_tree()["edges"]
    gold_edges: list[dict],        # {source_id, target_id, relation}
    id_to_index: dict[str, int],
) -> dict:
    """
    Returns per-relation-type and overall:
      precision, recall, f1, true_positives, false_positives, false_negatives
    Edge existence and edge-type-correctness are scored separately:
      - "detection": did we find *an* edge between this pair at all (any relation)?
      - "typed": did we find the *correct relation type* for that pair?
    """
```

Score both **detection** (any edge found between a gold pair) and **typed** (correct relation label) separately — a common mistake is collapsing these into one number, which hides whether misses are "found nothing" vs. "found something, wrong label."

### 1.3 CLI + CI wiring

- `tools/eval_dependency_tree.py` — loads a CSV + gold-edges file, runs `build_dependency_tree`, prints the metrics table (mirrors `tools/stress_test_reqcluster.py`'s existing pattern of a standalone script writing to `stress-results/`).
- Output goes to a new `eval-results/dependency_<dataset>_<timestamp>.md`, same convention as `stress-results/`.
- Add `tests/test_dependency_eval.py` — a fast unit test on a tiny synthetic gold set, asserting the scoring math itself is correct (independent of how good the engine is).

**Exit criterion:** running `python tools/eval_dependency_tree.py data/aerospace_requirements.csv` prints precision/recall/F1 by relation type, and you have a real baseline number to quote instead of "we think it's pretty good."

**Effort estimate:** 1–1.5 days (mostly gold-labeling time, not code).

## Phase 2 — spaCy-Based Artifact Extraction + Embedding Near-Match

This is the main fix. Two sub-changes, both inside the artifact-extraction path; `dependency_tree.py`'s Pass 0/1/2 orchestration and cycle-breaking/level-assignment logic are untouched.

### 2.1 Add spaCy, keep the offline story intact

- Add `spacy` + `en_core_web_sm` (~13MB, small enough to keep "offline, lightweight" mostly true — note this explicitly as a footprint increase from the current ~80MB-SBERT-only story, not something to hide).
- **Graceful degradation, matching the codebase's existing pattern** (same shape as the `sentence_transformers` try/except fallback in `embeddings.py`): if spaCy or the model isn't installed, fall back to the current regex extractor unchanged. Never a hard failure.

```python
try:
    import spacy
    _nlp = spacy.load("en_core_web_sm", disable=["ner", "lemmatizer"])
    _SPACY_AVAILABLE = True
except (OSError, ImportError):
    logging.warning("spaCy/en_core_web_sm unavailable — falling back to regex artifact extraction.")
    _SPACY_AVAILABLE = False
```

### 2.2 Replace NP-regex with dependency-parse-based SVO extraction

New function in `artifact_extractor.py`, `_extract_artifacts_spacy(sentence, verbs) -> list[str]`, used when `_SPACY_AVAILABLE`:

- For each token whose lemma is in the output/input verb bank, walk its dependency children:
  - **Active voice** (`dobj`, `attr`, `oprd`) → direct object is the artifact.
  - **Passive voice** (`nsubjpass`) → this is the fix for the biggest known gap: "the altitude report **shall be generated by** the nav unit" — today's regex only looks *after* an output verb and never fires here (the verb is passive; the "object" is grammatically the subject). spaCy's dependency parse tags `nsubjpass` directly, so passive-voice artifacts become a first-class case instead of a silent miss.
  - **Prepositional objects** (`prep` → `pobj`) for verb+preposition patterns ("depend **on** X", "respond **to** Y").
- **Coordination handling**: if the extracted noun's head has `conj` children ("altitude **and** heading data"), split into multiple separate artifacts instead of capturing only the first noun or a mangled compound — this is the second biggest known gap.
- Reuse the existing `_normalize()` (article-stripping, lowercasing, whitespace collapse) on whatever spaCy extracts, so downstream matching logic doesn't need to change.

**Consolidate the verb lexicons while you're in this code** (fixes the self-acknowledged sync-risk flagged in the module docstring): move `_OUTPUT_VERBS`/`_INPUT_VERBS` out of both `artifact_extractor.py` and `dependency_tree.py` into one new `backend/core/verb_lexicon.py`, imported by both. One source of truth, no more "must be kept in sync" comment.

### 2.3 Embedding near-match for artifact names (the promised-but-never-built step)

Currently: `producers.get(artifact_name)` requires **exact string equality** after normalization. Add a near-match pass in `build_artifact_index` (or a new function called right after it):

```python
def resolve_near_matches(
    producers: dict[str, list[int]],
    consumers: dict[str, list[int]],
    similarity_threshold: float = 0.80,
) -> tuple[dict[str, list[int]], dict[str, list[int]]]:
    """
    Embed each unique artifact-name string (reuse generate_embeddings — same
    SBERT model, same Redis/file cache, so this is nearly free after the main
    embedding pass already warmed the cache). For each producer artifact name,
    find consumer artifact names above `similarity_threshold` and merge them
    under a canonical name (the more frequent / shorter string, deterministic
    tie-break). Returns updated producer/consumer maps.
    """
```

- Deliberately reuses `embeddings.py`'s existing `generate_embeddings()` — artifact-name strings are short, there are far fewer unique artifact names than requirements, and they hit the same Redis cache. This is a small, cheap addition, not a new embedding pipeline.
- `0.80` cosine threshold is a starting point — **tune it against the Phase 1 harness's adversarial synonym set**, not by feel. This is exactly the kind of constant the harness exists to justify.
- Keep this **off by default and behind a flag** (`enable_artifact_near_match: bool`) initially, so Pass 0's precision doesn't regress silently while the threshold is being tuned — turn it on once the harness shows it's a net win.

### 2.4 Update `dependency_tree.py`'s Pass 0 rationale

Once artifacts can match via near-match, update the rationale string generation to say so explicitly (`"'{producer_name}' matched to '{consumer_name}' (synonym match, similarity 0.84)"` vs. today's implicit exact-match phrasing) — this is a small piece of Phase 3's explainability work but belongs here since it's a direct consequence of 2.3.

**Testing:**
- New `tests/test_artifact_extractor_spacy.py`: passive voice, coordination, and the fallback-to-regex path (mock spaCy import failure, assert output matches the old regex extractor's shape).
- Re-run Phase 1's harness on both the baseline and adversarial sets; the adversarial set specifically should show the biggest jump (that's what it was built to test).

**Exit criterion:** harness shows a measurable recall improvement on the adversarial set (passive voice / coordination / synonym cases) with precision not regressing on the original aerospace set. If precision drops meaningfully, the near-match threshold needs tightening before shipping.

**Effort estimate:** 2–3 days (spaCy integration + tests: ~1.5 days; near-match step + tuning against harness: ~1 day; consolidating verb lexicon: ~0.5 day).

## Phase 3 — On-Demand Per-Edge Explanation

Scoped specifically to avoid the scale/reliability trap discussed earlier: **no pipeline-wide LLM calls.** One call, only when a user clicks a specific edge.

### 3.1 Structured evidence, computed for free at edge-creation time (no LLM, do this first)

Every edge already implicitly carries the information needed to explain it — the fix is capturing it explicitly instead of collapsing it into one rationale string + float. Extend `DependencyEdge`:

```python
@dataclass
class DependencyEdge:
    source: int
    target: int
    relation: str
    weight: float
    rationale: str = ""
    evidence: dict = field(default_factory=dict)  # NEW

    def to_dict(self) -> dict:
        return {
            ...,
            "confidence_tier": self._confidence_tier(),  # NEW: "High" | "Medium" | "Low"
            "evidence": self.evidence,                    # NEW
        }
```

`evidence` captures, per pass: which pass fired (`pass_0_artifact_match` / `pass_1_explicit_reference` / `pass_2_sequential` / `pass_2_hierarchical`), the raw feature values that produced the weight (cosine similarity, matched artifact name, matched cue phrase, shared salient tokens, same-cluster flag), and — for Pass 0/1 specifically — the literal text span that triggered it, so the frontend can highlight it in-line rather than showing an abstract sentence.

`confidence_tier` maps weight ranges to **High / Medium / Low** for display — replaces "why exactly 0.73" scrutiny with a defensible bucket ("Pass 1 explicit references are always High; Pass 2 semantic edges are Medium/Low depending on similarity") — directly addresses the "explainable" complaint with zero LLM cost.

This alone should ship regardless of whether Phase 3.2 (LLM) ever gets built — it's the highest-leverage, lowest-risk explainability fix.

### 3.2 On-demand LLM justification, click-triggered only

**New endpoint:** `POST /api/dependencies/{session_id}/explain` — body `{source_index, target_index}`. Returns a natural-language justification generated from the edge's `evidence` object (not from raw text scanning — grounding the LLM call in already-computed structured evidence keeps it fast, cheap, and much less likely to hallucinate than asking it to re-derive the relationship from scratch).

**New prompt**, added to `llm_services/prompts.py` alongside `build_requirement_expansion_prompt`, following the same conventions already established there (versioned, strict-JSON-only, explicit "don't invent" constraints):

```python
EXPLAIN_EDGE_PROMPT_VERSION = "reqcluster-edge-explanation-v1"

def build_edge_explanation_prompt(
    source_text: str,
    target_text: str,
    relation: str,
    evidence: dict,
) -> str:
    """
    Given the two requirement texts, the inferred relation type, and the
    structured evidence that produced it, ask the model for a single
    plain-language paragraph explaining the dependency — grounded strictly
    in the provided evidence, not free re-analysis of the texts.
    """
```

**Reuse existing provider infrastructure wholesale** — `mock` / `local` / `openai`, same env vars, same offline-by-default posture as enrichment. The mock provider's deterministic explanation can just template the evidence object directly (e.g., "REQ-014 is linked to REQ-019 because both mention 'thermal limit' (similarity 0.71) and REQ-019's text contains the sequential cue 'after'.") — this means the feature **works fully offline by default**, same guarantee as everything else in the app; only the "real" prose version needs a configured LLM.

**Persistence + caching:** new table `DependencyExplanation(session_id, source_index, target_index, explanation_text, provider, generated_at)`, one row per (session, edge) — an edge only ever needs to be explained once per session; a second click is a cache hit, not a second LLM call. This is the mechanism that keeps the total LLM-call volume bounded regardless of dataset size (bounded by *how many edges a human actually clicks*, not by dataset size) — the exact property that made pipeline-wide Pass 2 verification untenable.

**Frontend:** in the dependency-tree view, clicking an edge shows the Phase 3.1 evidence panel immediately (no network wait, it's already in the payload), with an "Explain in plain language" button that fires the click-triggered call only if the user wants the prose version.

**Testing:** `tests/test_edge_explanation.py` — mock provider determinism test, cache-hit-on-second-request test, and a parser-hardening test mirroring the existing enrichment-response leniency pattern (small local models can return odd shapes here too — apply the same coercion approach that took enrichment success from 50%→88%).

**Exit criterion:** clicking any edge shows structured evidence instantly with no LLM call; clicking "Explain" produces a grounded paragraph, cached per edge, working offline via the mock provider by default.

**Effort estimate:** 1 day for structured evidence (3.1) + 1.5 days for the explain endpoint/prompt/caching (3.2) ≈ 2.5 days.

**Recommended order is strict, not parallel:** Phase 1 has to exist before Phase 2 can claim any improvement, and Phase 3.1 (structured evidence) is a near-prerequisite for Phase 3.2 (the LLM prompt is built *from* the evidence object).

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Near-match threshold merges genuinely distinct artifacts (false positive) | Ship behind a flag, tune against the adversarial harness set before enabling by default |
| spaCy model download breaks the "fully offline, one-time SBERT download" story | Document the added footprint explicitly (~13MB, one more one-time download); keep the regex fallback so the app never hard-fails without it |
| Gold-edge labeling is subjective / small-N | Treat Phase 1 numbers as directional, not definitive; expand with Dronology if time allows for a more credible external benchmark |
| LLM explanation hallucinating beyond the evidence | Prompt is explicitly grounded in the evidence dict, not free text re-analysis; mock provider (deterministic templating) is the default, so the feature works correctly with zero hallucination risk out of the box |
